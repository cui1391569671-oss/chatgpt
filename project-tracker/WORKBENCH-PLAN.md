# 双工作台需求与实施方案

## 已确认的需求

用户希望使用同一个已购买的域名，提供工作和私人两个工作台。
个人效率功能包括待办、笔记和日程；现有项目问题跟进表归入工作用途。
现有线上项目数据必须保留。

## 实现地址

- `/`：工作台选择入口。
- `/work`：工作工作台，包含工作待办、笔记、日程及项目问题入口。
- `/personal`：私人工作台，包含私人待办、笔记和日程。
- `/projects`：保留现有项目问题表地址，可从工作工作台进入。

## 数据隔离设计

两个工作台共用本人登录。私人范围保留原 `workspace`，工作范围使用 `workWorkspace`。
`GET /api/state` 已限制为项目字段，工作台接口按 scope 读取和写入。
这是同一使用者的用途隔离；若未来允许同事使用，必须增加独立权限。

## 数据与兼容要求

- 工作与私人分别保存待办、笔记、日程，列表、搜索、统计和导出均限制在当前范围。
- 现有项目、问题、归档、优先级及项目回收站保留在工作范围。
- 已存在的单工作台数据需要明确迁移归属，不能删除或默默搬入错误范围。
- 两个范围分别维护版本，避免私人修改导致工作页面保存冲突。
- 工作接口不得返回私人内容，工作保存和定时归档不得覆盖私人内容。
- 本版沿用现有记录，不执行数据库建表或初始化。

## 已确认的使用者范围

用户确认两个工作台都只有本人使用，沿用现有登录入口。
现有单工作台数据归入私人范围，原项目数据保留在工作用途。
当前仅修改草稿，生产发布仍等待确认。

## 验收范围

- 单域名的入口与两个工作台可以正常访问、导航和刷新。
- 两个工作台分别完成待办、笔记和日程的新增、编辑、删除、搜索及保存恢复。
- 工作统计不包含私人记录，私人统计不包含工作记录。
- 原项目表与归档功能正常，现有数据保留。
- 用工作账号直接请求私人页面及 API 时不能取得私人数据（若采用独立权限）。
- 并发修改、错误状态、空态及手机/桌面布局实际验证。
- 最后根据确认的版本合并并验证真实生产部署，草稿或本地测试不等于上线完成。
